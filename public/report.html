CHAPTER 1 - INTRODUCTION TO CONCURRENCY CONTROL & EVENT REGISTRATION

1.1 Introduction to Concurrency Anomalies

In modern multi-threaded operating systems and distributed web backends, concurrency arises when multiple execution contexts (threads, processes, or asynchronous microtasks) simultaneously access shared mutable resources in memory. While concurrent architectures maximize CPU utilization and request throughput, they introduce severe race conditions when shared state modifications are not strictly synchronized.

In high-demand event ticketing, railway Tatkal reservations, and university symposium registrations, the primary contended resource is a finite numerical integer: remaining seat capacity. When contention surges—specifically when only 1 or 2 seats remain—concurrent buyer requests arrive at the server within microsecond intervals. Uncontrolled interleaving triggers a classical Time-of-Check to Time-of-Use (TOCTOU) race condition: multiple threads read identical stale capacity values before any write operation commits, driving capacity below zero ($C_{remaining} < 0$) and minting phantom duplicate tickets.

1.2 Need for Synchronization & Mutex

At the machine instruction level, decrementing an integer in RAM (such as remaining_tickets--) is non-atomic and executes across three discrete CPU cycles:

  • MOV EAX, [remaining_tickets] — Load current memory value into CPU register.
  • SUB EAX, 1 — Decrement register value in the Arithmetic Logic Unit.
  • MOV [remaining_tickets], EAX — Store decremented register value back into memory.

If an asynchronous event-loop turn, context switch, or database I/O latency occurs between Step 1 and Step 3, concurrent execution paths read stale state. Mutual Exclusion (Mutex) is the foundational Operating Systems primitive that enforces critical section serialization: it guarantees that exactly one thread modifies capacity at any instant.

1.3 Basic Working of Mutex & Critical Section

A Critical Section is a sequence of instructions accessing shared mutable variables. Dijkstra (1965) established three mandatory criteria for any valid concurrency solution:

  1. Mutual Exclusion: At most one thread executes inside the critical section at any time: $ orall t, |\mathcal{C}(t)| \le 1$.
  2. Progress: If the critical section is vacant, waiting threads cannot be postponed indefinitely from entering.
  3. Bounded Waiting: A bound exists on how many times other threads enter before a waiting thread enters, eliminating starvation ($O(k)$ queue length).

1.4 Applications of Mutex in High-Contention Ticketing

Concurrency synchronization is essential across commercial and industrial infrastructure:

  • IRCTC Tatkal Railway Reservations: Over 1.5 million users contend for limited berths at 10:00 AM IST daily; strict critical section locks prevent overselling physical train berths.
  • Global Tech Summits & Hackathons (SYNNEXA): High-demand squad pass registrations where multiple developer teams compete for final conference seats simultaneously.
  • Financial Banking & UPI Gateways: Account balance transactions requiring serialized debit/credit sequences to eliminate double-spend anomalies.
  • Airline Flight Inventory: Seat assignment systems requiring bijective 1-to-1 mappings between passenger tickets and aircraft seats.

CHAPTER 2 - MATHEMATICAL PRINCIPLES OF CONCURRENCY CONTROL & MUTEX

2.1 State Invariants and Shared Data Representation

Let an event have initial capacity $C_{total} \in \mathbb{N}^+$. Let $\mathcal{R}(t) = {r_1, r_2, \dots, r_m}$ denote the set of confirmed tickets issued up to timestamp $t$. Remaining capacity $C_{remaining}(t)$ is defined as:

C_remaining(t) = C_total - |R(t)|

The fundamental system safety invariants that must hold for all timestamps $t \ge 0$:

  • Invariant 1 (Non-Negative Capacity): $ orall t \ge 0, \quad 0 \le C_{remaining}(t) \le C_{total}$.
  • Invariant 2 (Bijective Slot Integrity): $ orall r_i, r_j \in \mathcal{R}(t), \quad r_i e r_j \implies ext{TicketCode}(r_i) e ext{TicketCode}(r_j) \land |\mathcal{R}(t)| \le C_{total}$.

2.2 Mutual Exclusion Property (Formal Proof)

Let $\mathcal{T} = {T_1, T_2, \dots, T_n}$ denote concurrent reservation threads. Let $\mathcal{C}(t) \subseteq \mathcal{T}$ be the set of threads actively executing inside the critical section at time $t$.

Theorem 1 (Mutual Exclusion): ∀ t ≥ 0,   |C(t)| ≤ 1

Proof by Contradiction: Assume distinct threads $T_a, T_b \in \mathcal{T}$ ($a e b$) execute simultaneously in $\mathcal{C}(t^*)$ at timestamp $t^*$.

  1. A thread enters $\mathcal{C}(t)$ if and only if _locked is transitioned from false to true.
  2. Assume $T_a$ acquired the lock at $t_a \le t^*$, setting _locked = true and _currentOwner = Ta.
  3. When $T_b$ attempts acquisition at $t_b \le t^*$, it evaluates if (!this._locked).
  4. Because $T_a$ has not called _release(), _locked remains true.
  5. $T_b$ evaluates the check to false, is pushed into _queue, and returns an unfulfilled Promise.
  6. Thus, $T_b$ cannot execute inside $\mathcal{C}(t^*)$, contradicting the assumption. Hence, $|\mathcal{C}(t)| \le 1$ holds for all $t$. ◼

2.3 Progress and Bounded Waiting Proof (Starvation Elimination)

Let thread $T_i$ request the lock at timestamp $t_{req}(T_i)$. Let $W(T_i)$ denote the number of other threads granted access before $T_i$. Under our strict FIFO queue discipline:

W(T_i) = |{ T_j ∈ Q : t_req(T_j) < t_req(T_i) }| = k < ∞

Because critical section duration is bounded by $\Delta t_{CS} \le 50 ext{ms}$, waiting time is bounded: $ ext{WaitTime}(T_i) \le k \cdot \Delta t_{CS} < \infty$. This mathematically eliminates thread starvation.

2.4 Atomic Test-and-Set and Asynchronous Transitions

In multi-threaded C/C++, atomic operations rely on CPU instructions (CMPXCHG / XCHG). In Node.js, JavaScript executes on a single-threaded V8 event loop. Synchronous execution of a microtask is non-preemptive: evaluating if (!this._locked) and setting this._locked = true in the same synchronous turn operates with hardware-equivalent atomicity.

2.5 Time-of-Check to Time-of-Use (TOCTOU) Race Hazard Formulation

When synchronization is disabled (Mutex OFF), inventory validation and state mutation decouple across asynchronous boundaries:

  1. t0: Thread $T_1$ reads $C_{remaining} = 1$. Evaluates check: $1 > 0 \implies ext{VALID}$.
  2. t1: Thread $T_1$ awaits asynchronous network I/O / payment delay.
  3. t2: Thread $T_2$ arrives, reads $C_{remaining} = 1$ (STALE!). Evaluates check: $1 > 0 \implies ext{VALID}$.
  4. t3: Thread $T_2$ begins asynchronous delay.
  5. t4: Thread $T_1$ finishes, writes $C_{remaining} \leftarrow 1 - 1 = 0$, mints Ticket #1.
  6. t5: Thread $T_2$ finishes, writes $C_{remaining} \leftarrow 0 - 1 = -1$, mints Ticket #2.

This sequence violates Invariant 1: $C_{remaining}(t_5) = -1 < 0$. Two tickets are confirmed for a single seat.

2.6 State Verification and Invariant Violation Detection

The system continuously audits runtime state against formal criteria:

Audit Parameter Safety Condition Violation Classification System Action
Capacity Lower Bound $C_{remaining}(t) \ge 0$ OVERSOLD / RACE HAZARD Trigger Red Anomaly Badge, Log Violation
Capacity Upper Bound $C_{remaining}(t) \le C_{total}$ INVENTORY LEAK Halt Batch Releases, Audit Ledger
Mutual Exclusion $|\mathcal{C}(t)| \le 1$ LOCK INTEGRITY COLLAPSE Enforce FIFO Mutex Serialization
Ticket Bijectivity $|\mathcal{R}(t)| = C_{total} - C_{remaining}(t)$ PHANTOM MINTING Rollback Unverified Bookings, Issue Refund

3.4 Keyed Mutex Registry for Fine-Grained Locking

A global lock creates Amdahl's bottleneck: buyers for Event 1 would lock out buyers for Event 2. The Keyed Mutex Registry allocates independent locks per event key:

NODE.JS LTS
01/**
02 * KeyedMutexRegistry - Fine-grained lock management per Hackathon / Resource
03 *
04 * Ensures bookings for Hackathon A don't lock or block Hackathon B,
05 * but all concurrent bookings within the same Hackathon queue up in strict FIFO order.
06 */

18 * @returns {Mutex}

21 const keyStr = String(key);
22 if (!this._registry.has(keyStr)) {

24 this._registry.set(keyStr, mutex);

31 }

34 * Execute an asynchronous task inside the Critical Section of a keyed Mutex

39 */

46 release();
47 }
48 }

57 }
58 return result;
59 }
60

62 * Reset all mutexes
63 */

67 }
68 }
69}

APPENDIX B - LINE-BY-LINE EXPLANATION OF CODE

This section provides a rigorous breakdown of key functions, state variables, and architectural logic:

1. `Mutex` Class Constructor (`src/core/Mutex.js`)

  • this._locked = false;: Binary semaphore state flag. When false, the critical section is vacant; when true, an active thread owns the lock.
  • this._queue = [];: Array-backed FIFO wait queue storing pending thread grants, guaranteeing Dijkstra's Bounded Waiting criterion.
  • this._currentOwner = null;: Diagnostic identifier tracking the active thread ID for microsecond audit logging.

2. `acquire(threadId, metadata)` Method

  • Lines 14–19 (Fast-Path Acquisition): If !this._locked evaluates to true, the lock is vacant. Sets _locked = true and immediately returns Promise.resolve(() => this._release(threadId)) without event-loop suspension.
  • Lines 21–34 (Slow-Path Enqueuing): If _locked is true, wraps execution inside an unfulfilled new Promise((resolve) => ...) and pushes a grant closure into this._queue, safely suspending the thread.

3. `_release(threadId)` Method

  • Lines 37–44 (FIFO Grant & Dequeue): If this._queue.length > 0, executes this._queue.shift().grant(), transferring ownership directly to the oldest waiting thread in strict $O(1)$ time, eliminating starvation. If queue is empty, reverts _locked = false.

4. `KeyedMutexRegistry.getMutex(key)` Method

  • Queries internal Map for key. If absent, instantiates dedicated Mutex('event-mutex-' + key), ensuring independent events never contend for the same lock instance.

5. Critical Section Execution in `BookingService.js`

  • const release = await mutex.acquire(threadId);: Asynchronously awaits lock grant before evaluating shared database state.
  • try { ... } finally { release(); }: Ensures lock release is unconditionally invoked even if JSON serialization or database writes throw unexpected runtime exceptions, eliminating deadlocks.

6. Atomic Check-and-Decrement Logic

  • if (currentEvent.remaining_tickets <= 0): Re-reads latest capacity inside the critical section. If zero, immediately rejects with HTTP 409 SOLD_OUT.
  • const updatedSeats = currentEvent.remaining_tickets - 1;: Safely decrements capacity without risk of interleaved writes.
  • db.updateHackathon(...) & db.createBooking(...): Commits decremented state and generates cryptographic ticket code.

7. Automated Refund Trigger in `public/app.js`

  • completeBookingWithBackend(payload): Dispatches booking payload to /api/book.
  • catch (err) { if (isSoldOut) { openRefundNoticeModal(...); } }: Intercepts HTTP 409 status code and displays the formal refund protection modal with tracking ID and 5–7 day timeline.

8. ACID JSON Persistence in `Database.js`

  • fs.writeFileSync(tmpPath, JSON.stringify(data)): Writes state to temporary file.
  • fs.renameSync(tmpPath, finalPath): Commits data via an OS-level atomic inode swap, preventing corrupted partial writes during system crashes.
