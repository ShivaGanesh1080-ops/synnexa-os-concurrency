ABSTRACT

In modern high-throughput web applications, flash registration portals, ticket booking platforms, and university workshop enrollment systems, concurrent access to mutable state represents a primary vector for critical data hazards. When available capacity is low—specifically when only one or two seats remain—uncontrolled simultaneous requests trigger Time-of-Check to Time-of-Use (TOCTOU) race conditions. Multiple execution threads concurrently read stale capacity values before write operations commit, resulting in severe overbooking and system invariant violation where remaining capacity drops below zero ($C_{rem} < 0$).

This project proposes and implements “SyncReg OS”, a full-stack, enterprise-grade Event & Workshop Registration System engineered to solve the classical Critical Section Problem in software systems. The architecture implements an asynchronous Mutex (Mutual Exclusion Lock) primitive integrated with a strict First-In, First-Out (FIFO) wait queue. This design satisfies all three classical Dijkstra criteria: Mutual Exclusion, Progress, and Bounded Waiting ($O(k)$ starvation elimination).

To prevent coarse-grained bottlenecks, a Keyed Mutex Registry provides fine-grained, per-resource locking, enabling independent events to process registrations in parallel. The full-stack platform features a dynamic seat allocator, real-time Server-Sent Events (SSE) telemetry pipeline, interactive head-to-head duel simulator, visual attendee seat grid, and an empirical stress-testing suite. Experimental evaluation under high load (50 threads competing for 2 seats) proves that the Mutex synchronization mechanism completely eliminates overbooking (100% data integrity with zero negative capacity anomalies), whereas unsynchronized execution results in an overbooking hazard of 18 phantom registrations.

1. INTRODUCTION

Multi-threaded and event-driven computing architectures represent the backbone of contemporary cloud infrastructure. By multiplexing I/O and distributing workloads across multi-core processors, modern backends achieve remarkable throughput. However, concurrent execution introduces fundamental synchronization challenges whenever multiple threads share access to mutable memory states.

In high-level programming environments, high-level decrement expressions such as capacity = capacity - 1 or capacity-- appear syntactically atomic. At the hardware architecture level, however, modern Central Processing Units (CPUs) decompose this single instruction into three distinct low-level operations: 

1. MOV  EAX, [remainingCapacity]  ; LOAD: Read shared memory into CPU register
2. SUB  EAX, 1                    ; COMPUTE: Decrement register in ALU
3. MOV  [remainingCapacity], EAX  ; STORE: Write register contents back to RAM

If the operating system kernel's preemptive scheduler initiates a context switch or timer interrupt between Step 1 and Step 3, interleaved execution by competing threads corrupts the state. When multiple users submit bookings simultaneously during high-demand workshops, this non-atomic instruction sequence manifests as a catastrophic Check-Then-Act Race Condition.

This project implements a complete, end-to-end full-stack software system that models, analyzes, and mitigates this concurrency hazard using fundamental Operating System synchronization primitives.

2. RELATED WORK

The challenge of mutual exclusion in concurrent computation was originally formalized by Edsger W. Dijkstra in 1965. Early pure-software synchronization algorithms, such as Peterson’s Algorithm (1981) and Dekker’s Algorithm, successfully enforced mutual exclusion for two competing processes using busy-waiting turn flags. Lamport extended this to $N$ processes with the Bakery Algorithm. However, software-only busy-waiting algorithms suffer from severe memory barriers, CPU cache thrashing, and are unsuitable for asynchronous I/O architectures.

Modern computer architectures introduce hardware-supported atomic read-modify-write instructions, including Test-and-Set (TAS), Compare-and-Swap (CAS / CMPXCHG on x86), and Load-Linked / Store-Conditional (LL/SC on ARM). While spinlocks leverage CAS in kernel spaces where hold durations are extremely short ($< 2$ context switches), user-space applications require non-blocking, yield-capable sleep-locks.

In web and microservices architectures, distributed locking mechanisms such as Redis Redlock and relational database row-level locking (SELECT ... FOR UPDATE) are deployed. This project bridges systems-level OS theory with application-tier software engineering by designing an asynchronous, queue-based Ticket/FIFO Mutex in pure Node.js, eliminating spinlock CPU burn while guaranteeing mathematical bounds on waiting times.

3. PROBLEM STATEMENT

Product #8 Specification (Operating Systems Lab):
“Several users attempt to register when only one or two places remain. How can the remaining capacity be updated correctly?”

When workshop seat capacity is abundant, race conditions remain latent and hidden. However, when remaining capacity reaches critical scarcity ($C_{remaining} \in \{1, 2\}$), a sudden surge of registration requests triggers the Time-of-Check to Time-of-Use (TOCTOU) hazard: 

Time   Thread 1 (User A)                  Thread 2 (User B)                  Memory State
-----------------------------------------------------------------------------------------
t0     READ remainingCapacity (=1)        .                                  C = 1
t1     .                                  READ remainingCapacity (=1)        C = 1 (Stale Read)
t2     CHECK (1 > 0) -> TRUE              .                                  C = 1
t3     .                                  CHECK (1 > 0) -> TRUE              C = 1 (Stale Check)
t4     DECREMENT (1 - 1 = 0)              .                                  Reg1 = 0
t5     .                                  DECREMENT (1 - 1 = 0)              Reg2 = 0
t6     WRITE back (0)                     .                                  C = 0
t7     .                                  WRITE back (0 - 1 = -1)            C = -1 [OVERBOOKING!]
t8     CONFIRM Ticket A                   CONFIRM Ticket B                   2 Tickets for 1 Seat!

Consequences of Unsynchronized Execution:

  • Physical Capacity Violation: Confirmed attendee tickets exceed venue seats.
  • State Invariant Breakdown: System invariant $0 \le C_{remaining} \le C_{total}$ is violated, dropping to negative values ($-1, -7, -18$).
  • Duplicate Bookings: Users submitting multiple rapid clicks bypass duplicate email checks due to interleaved verification.

  • FR-6 (Real-Time Telemetry): The system must stream lock acquisition, critical section entry, and release logs via Server-Sent Events (SSE).

4.2 Non-Functional Requirements

  • NFR-1 (Mutual Exclusion Invariant): At all points in time $t$, $0 \le C_{remaining}(t) \le C_{total}$, and $C_{remaining}(t) + |Confirmed Registrations| = C_{total}$.
  • NFR-2 (Bounded Waiting / Zero Starvation): Lock granting must follow strict First-In, First-Out (FIFO) queue ordering, guaranteeing bounded wait time $O(k)$.
  • NFR-3 (High Throughput & Low Latency): Lock acquisition and critical section overhead must execute in under 15ms under standard contention.
  • NFR-4 (Deadlock Freedom): The system must guarantee that Coffman conditions (specifically Circular Wait and Hold & Wait) are broken.
  • NFR-5 (Zero External Dependencies): Built entirely on native Node.js core libraries (http, fs, events) for maximum portability.

8.2 OS Process / Thread Lifecycle Mapping

The system models threads through classical Operating System states:

  • NEW: HTTP request is ingested and parsed by the network socket.
  • READY: Request thread is dispatched to the event loop, requesting the resource lock.
  • BLOCKED / WAITING: If the mutex is occupied, the Promise resolver is queued into this._queue; the thread yields CPU.
  • RUNNING (Critical Section): Lock granted; thread executes duplicate checking, capacity verification, and atomic mutation.
  • TERMINATED: Lock released in finally block; HTTP response emitted with confirmed ticket or sold-out notice.

11. CORE IMPLEMENTATION & ALGORITHMS

11.1 The Asynchronous Mutex Primitive (`Mutex.js`)

class Mutex {
  constructor(name = 'default-mutex') {
    this.name = name;
    this._locked = false;
    this._queue = []; // Strict FIFO Queue for Bounded Waiting
    this._currentOwner = null;
  }

  acquire(requesterId) {
    if (!this._locked) {
      this._locked = true;
      this._currentOwner = requesterId;
      return Promise.resolve(() => this._release(requesterId));
    }
    // Lock Contention: Enqueue in FIFO line (Zero Starvation)
    return new Promise((resolve) => {
      this._queue.push({
        requesterId,
        grant: () => {
          this._locked = true;
          this._currentOwner = requesterId;
          resolve(() => this._release(requesterId));
        }
      });
    });
  }

  _release(ownerId) {
    if (this._queue.length > 0) {
      const nextInQueue = this._queue.shift(); // FIFO Dispatch
      nextInQueue.grant();
    } else {
      this._locked = false;
      this._currentOwner = null;
    }
  }
}
